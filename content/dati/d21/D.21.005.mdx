<Scene title="Git per i modelli">
I file SQL e YAML del progetto stanno in un **repository Git**. Git conserva ogni versione di ogni file. Il lavoro si fa su un **branch** (ramo): una copia di lavoro separata dove si prova senza toccare quella principale (di solito `main`).

<Log lines={[
  "git switch -c cambia-regola-ricavi    # nuovo branch di lavoro",
  "# ...modifichi models/marts/fct_ordini.sql...",
  "git add models/marts/fct_ordini.sql",
  "git commit -m 'Esclude i rimborsi dai ricavi'",
  "git push -u origin cambia-regola-ricavi",
]} caption="Sul tuo branch puoi sbagliare: main non cambia." />

Poi si apre una **pull request** (richiesta di unione): dice ai colleghi «ho cambiato questo, controllate». Un collega legge il codice, commenta, approva. Solo allora il branch viene **unito** (*merge*) in `main`.

<Flow
  caption="Il percorso di una modifica, dal branch a main."
  steps={[
    { icon: "code", title: "Branch", text: "Si lavora su una copia" },
    { icon: "mail", title: "Pull request", text: "«Controllate la mia modifica»" },
    { icon: "eye", title: "Revisione", text: "Un collega legge e approva" },
    { icon: "check", title: "Merge", text: "Entra in main" },
  ]}
/>

<Callout kind="regola">
Su `main` c'è solo ciò che è stato **rivisto e testato**. Nessuno scrive direttamente su `main`.
</Callout>

<Callout kind="attenzione">
In Git non vanno mai password o chiavi. Per dbt, `profiles.yml` resta fuori dal repository e le credenziali si leggono dalle variabili d'ambiente. Una cartella `target/` o `logs/` non si versiona: sono file prodotti da dbt, da ignorare nel `.gitignore`.
</Callout>

<Say who="assistente">La pull request non è sfiducia. È un secondo paio di occhi: ne vede sempre di più di uno.</Say>
</Scene>

<Scene title="Sviluppo e produzione">
Un progetto dbt gira in due **ambienti**:

| Ambiente | Chi lo usa | Dove scrive | Quando gira |
|---|---|---|---|
| sviluppo (dev) | tu, mentre lavori | uno schema personale, ad esempio `dbt_marta` | a mano, con `dbt build` |
| produzione (prod) | dashboard e colleghi | lo schema ufficiale, ad esempio `analytics` | in automatico, ogni notte |

In `profiles.yml` si definiscono due **target**:

<Log lines={[
  "cesto:",
  "  target: dev",
  "  outputs:",
  "    dev:",
  "      type: postgres",
  "      host: localhost",
  "      port: 5432",
  "      user: marta",
  "      password: \"{{ env_var('DBT_PASSWORD') }}\"",
  "      dbname: cesto",
  "      schema: dbt_marta",
  "      threads: 4",
  "    prod:",
  "      type: postgres",
  "      host: localhost",
  "      port: 5432",
  "      user: marta",
  "      password: \"{{ env_var('DBT_PASSWORD') }}\"",
  "      dbname: cesto",
  "      schema: analytics",
  "      threads: 4",
]} caption="Esempio con PostgreSQL. Nel file la password è letta da una variabile, mai scritta." />

Lo stesso codice, due destinazioni. `dbt build` scrive nello schema `dbt_marta`; `dbt build --target prod` scrive in `analytics`. Con `ref` dbt trova i nomi giusti in entrambi i casi.

<Callout kind="trucco">
`dbt build` esegue modelli e test **insieme**, nell'ordine del grafo: se un test fallisce, i modelli che ne dipendono non vengono costruiti. È il comando giusto per sviluppo e rilascio.
</Callout>

<Say who="sensei">Provare in sviluppo costa niente. Provare in produzione costa la fiducia di chi legge il report.</Say>
</Scene>

<Scene title="Integrazione continua in parole semplici">
Rivedere a occhio non basta: una persona può non vedere che un test si è rotto. L'**integrazione continua** (CI, *continuous integration*) è un controllo **automatico** che parte a ogni pull request:

<Guided
  steps={[
    "Marta apre una pull request: il sistema di CI (ad esempio GitHub Actions) si accorge e parte.",
    "La CI costruisce i modelli in uno schema temporaneo, separato dalla produzione.",
    "La CI lancia i test (dbt build): se uno fallisce, la pull request resta rossa.",
    "Il collega rivede il codice e vede anche l'esito dei test: se è verde e il codice è giusto, approva.",
    "Solo a questo punto si unisce in main. Un lavoro automatico notturno rilascia in produzione.",
  ]}
/>

Per non ricostruire tutto a ogni modifica, la CI può costruire **solo ciò che è cambiato e ciò che ne dipende**. Con dbt Core si usa il confronto con lo stato di produzione:

<Log lines={[
  "dbt build --select state:modified+ --defer --state prod-artifacts/",
]} caption="Costruisce i modelli modificati e quelli a valle; per gli altri legge la produzione. Serve il file manifest.json salvato dall'ultimo rilascio in prod-artifacts/." />

<Callout kind="curiosita">
Il servizio a pagamento dbt Cloud offre la stessa idea già pronta, con un'impostazione. Con dbt Core, gratuito, la scrivi tu nel sistema di CI.
</Callout>

<Scene title="Rapporto finale">
<Recap xp={20}>
- Le modifiche si fanno su un branch, si rivedono con una pull request e si uniscono in main solo con test verdi. Nessuno scrive su main.
- Sviluppo e produzione hanno schemi diversi, scelti dal target (dev o prod): si prova in sviluppo, la produzione serve alle persone.
- L'integrazione continua costruisce e testa in automatico a ogni pull request, in uno schema temporaneo. Password e chiavi mai in Git.
</Recap>
