<Scene title="Che cos'è una transazione">
Una **transazione** è un gruppo di istruzioni SQL trattato come **un'unica operazione indivisibile**: o riescono tutte, o non ne riesce nessuna.

Si scrive così:

<Log lines={[
  "BEGIN;",
  "UPDATE conti SET saldo = saldo - 100 WHERE id = 1;",
  "UPDATE conti SET saldo = saldo + 100 WHERE id = 2;",
  "COMMIT;",
]} caption="Il bonifico come transazione." />

- `BEGIN` apre la transazione.
- `COMMIT` la **conferma**: le modifiche diventano definitive e visibili a tutti.
- `ROLLBACK` la **annulla**: tutto torna come prima di `BEGIN`.

Se il server si spegne prima del `COMMIT`, al riavvio il database annulla da solo la transazione incompleta. I saldi restano 500 e 200.

<Compare
  caption="Lo stesso guasto, con e senza transazione."
  left={{ title: "Senza transazione", points: ["Tolti 100 euro a Giulia", "Il server si spegne a metà", "100 euro spariti nel nulla"] }}
  right={{ title: "Con transazione", points: ["BEGIN, poi le due modifiche", "Spegnimento prima del COMMIT", "Annullata da sola: saldi 500 e 200"] }}
/>

<Callout kind="trucco">
Pensa al carrello di un negozio: puoi riempirlo e svuotarlo quanto vuoi. Solo alla cassa (il COMMIT) il conto diventa vero.
</Callout>

<Say who="assistente">Senza BEGIN, ogni istruzione è già una transazione da sola, con il suo COMMIT automatico. Per questo, nel bonifico a due passi, serve il BEGIN esplicito.</Say>
</Scene>

<Scene title="ACID: le quattro garanzie">
Una transazione seria offre quattro garanzie. Le iniziali formano la sigla **ACID**.

- **A, Atomicità**: tutto o niente. Non esistono transazioni a metà.
- **C, Consistenza**: i dati rispettano sempre le regole (per esempio «il saldo non è negativo»). Una transazione che le viola viene rifiutata.
- **I, Isolamento**: due transazioni che corrono insieme non si pestano i piedi.
- **D, Durabilità**: dopo il COMMIT il dato resta, anche se un attimo dopo salta la corrente.

</Callout>

<Scene title="ROLLBACK: tornare indietro">
Giulia prova a mandare **600 euro**, ma ne ha solo 500. La tabella ha la regola `CHECK (saldo >= 0)`.

<Log lines={[
  "BEGIN;",
  "UPDATE conti SET saldo = saldo - 600 WHERE id = 1;",
  "ERRORE: il nuovo valore viola il vincolo conti_saldo_check",
  "ROLLBACK;",
  "SELECT id, saldo FROM conti ORDER BY id;",
]} caption="Il vincolo blocca la prima modifica." />

<Log lines={[
  "id | saldo",
  "1  | 500.00",
  "2  | 200.00",
]} caption="Risultato dell'ultima SELECT: nulla è cambiato." />

<Callout kind="attenzione">
In PostgreSQL, dopo un errore dentro una transazione, ogni altra istruzione viene rifiutata finché non scrivi `ROLLBACK`. In MySQL, invece, la transazione di solito resta aperta e decidi tu.
</Callout>

`ROLLBACK` serve anche quando sei **tu** a cambiare idea: hai scritto un `UPDATE` senza `WHERE` per sbaglio? Se sei ancora dentro la transazione, annulli e nessuno se ne accorge.

<Say who="sensei">Prima di ogni modifica importante: BEGIN. Poi controlli. Poi decidi: COMMIT o ROLLBACK.</Say>
</Scene>

<Scene title="L'isolamento, in parole semplici">
Mentre la transazione di Giulia è aperta (ha tolto 100 ma non ha ancora scritto COMMIT), un'impiegata esegue `SELECT saldo FROM conti WHERE id = 1`. Che cosa vede?

<Log lines={[
  "Transazione A (Giulia)           Transazione B (impiegata)",
  "BEGIN;",
  "UPDATE ... saldo = saldo - 100;",
  "                                 SELECT saldo ... id = 1;   -> 500.00",
  "COMMIT;",
  "                                 SELECT saldo ... id = 1;   -> 400.00",
]} caption="Livello predefinito di PostgreSQL: READ COMMITTED." />

B vede **solo dati già confermati**. Prima del COMMIT di A vede 500. Dopo, vede 400. Non vede mai il «mezzo bonifico».

Il **livello di isolamento** decide quanto B è protetto dai cambiamenti che arrivano mentre lavora:

- **READ COMMITTED** (predefinito in PostgreSQL): ogni istruzione vede i dati confermati fino a quel momento.
- **REPEATABLE READ**: B vede una «fotografia» scattata all'inizio e non cambia mai, per tutta la transazione.
- **SERIALIZABLE**: come se le transazioni andassero una dopo l'altra. Il più sicuro, il più lento, a volte rifiuta una transazione che va ritentata.

<Callout kind="curiosita">
In MySQL (InnoDB) il livello predefinito è REPEATABLE READ, non READ COMMITTED. Stessi comandi, comportamenti leggermente diversi: controlla sempre il database che usi.
</Callout>

<Say who="assistente">Più isolamento vuol dire più sicurezza e meno velocità. Si sceglie caso per caso.</Say>
</Scene>

<Scene title="Rapporto finale">
<Recap xp={25}>
- Caso chiuso: con BEGIN e COMMIT i 100 euro di Giulia non possono sparire a metà; se il server si spegne, restano 500 e 200.
- Una transazione raggruppa più istruzioni: o riescono tutte (COMMIT) o non ne resta nessuna (ROLLBACK).
- ACID: atomicità, consistenza, isolamento, durabilità.
- L'isolamento decide che cosa vede una transazione delle altre: in PostgreSQL, di base, solo dati già confermati.
</Recap>
