<Scene title="Cos'è un portfolio e dove sta">
Un **portfolio** è una raccolta di tuoi progetti, che mostra come lavori. Per l'analisi dei dati il luogo più usato è **GitHub** (github.com): un sito gratuito dove si conservano file e codice, con la storia di tutte le modifiche. Ogni progetto sta in un **repository**, una cartella online.

Si può aggiungere una pagina web semplice con **GitHub Pages** (pages.github.com), sempre gratuita, per presentare i progetti migliori. Non è obbligatoria: un profilo ordinato basta.

<Scene title="Il README: la porta d'ingresso">
Il **README** è il file di testo che GitHub mostra per primo in ogni repository. Se è chiaro, il progetto si capisce senza aprire altro. Struttura consigliata:

1. **Titolo** che dice la risposta o il tema.
2. **Domanda** a cui rispondi, in due righe.
3. **Dati**: fonte, licenza, data di scarico.
4. **Metodo**: gli strumenti e i passi principali.
5. **Risultati**: un grafico chiave e la conclusione.
6. **Come rifare l'analisi**: quali file lanciare e in quale ordine.
7. **Limiti** e idee per il futuro.

Una cartella ordinata aiuta: `dati/grezzi`, `notebook`, `report`, e un file con l'elenco delle librerie usate.

<Callout kind="trucco">
Prova il **test del vicino**: dai il README a qualcuno che non conosce il progetto. Se in un minuto sa dirti domanda e conclusione, funziona.
</Callout>

<Say who="sensei">Il codice più brillante, senza README, è una stanza chiusa a chiave. Apri la porta.</Say>
</Scene>

<Scene title="Pochi progetti, ben fatti">
**Meglio un progetto buono che dieci mediocri.** Due o tre progetti completi, ognuno con una domanda vera, dati con fonte, un report e un README, dicono molto di più di venti esercizi sparsi.

Cosa mostrare:

- un progetto **dal dato al report** (come quello del modulo);
- uno che mostri **SQL** o un database;
- uno che mostri un **cruscotto** o una visualizzazione chiara.

Cosa lasciare fuori:

- esercizi copiati dai tutorial senza modifiche;
- progetti a metà senza spiegazione (o segnali che sono in corso);
- tutto ciò che non sapresti spiegare a voce.

<Callout kind="regola">
Per ogni progetto prepara **una spiegazione di due minuti**: domanda, dati, cosa hai scoperto, cosa faresti ora. È la stessa che ti chiederanno al colloquio.
</Callout>

<Say who="assistente">Se in un progetto hai usato aiuti (tutorial, strumenti di IA, esempi altrui), dillo nel README. Dichiararlo è una forza, non una debolezza.</Say>
</Scene>

<Scene title="Cosa non pubblicare mai">
Su un repository pubblico **chiunque** può leggere tutto, anche la storia delle vecchie versioni.

Non si pubblicano mai:

- **dati personali** di persone reali: nomi, email, telefoni, indirizzi. Se un dataset li contiene, non va pubblicato (GDPR);
- **dati riservati** di un'azienda o di una scuola, anche se «li hai solo guardati»;
- **password, chiavi di accesso e token**: se finiscono online per sbaglio, vanno considerate bruciate e sostituite;
- informazioni su di te che non vuoi diffondere: se hai meno di 18 anni, parlane con un genitore o con chi ti segue prima di pubblicare nome, scuola o foto.

<Callout kind="attenzione">
Cancellare un file da GitHub non lo cancella dalla storia. La regola è: **se non l'hai pubblicato, non può uscire**. Controlla prima di fare «push».
</Callout>

<Say who="sensei">Una chiave caricata per errore è un incidente di sicurezza. Il portfolio non vale questo rischio.</Say>
