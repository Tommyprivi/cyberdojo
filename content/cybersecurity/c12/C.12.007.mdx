<Scene title="Il controllo che nessuno ripete">
Alla «Colombo Servizi» l'hardening del server è stato fatto con cura a gennaio. A ottobre un controllo a campione trova: accesso root via SSH di nuovo permesso, un account con UID 0 in più, un file di password leggibile da tutti. Nessuno ricorda di aver cambiato niente.

La domanda del caso: **come si scopre una configurazione che «deriva» nel tempo, senza controllare tutto a mano ogni settimana?**

<Say who="sensei">La sicurezza di un server non si fa una volta. Si fa, si misura, si rifà. Una macchina che non si controlla tende a tornare insicura.</Say>
</Scene>

<Scene title="Le regole di un buon controllo">
Uno script di controllo (in inglese *audit script*) dovrebbe essere:

- di **sola lettura**: non cambia mai la configurazione, riferisce e basta (la correzione la fa una persona, con un permesso);
- **chiaro**: stampa una riga per ogni controllo, con PASS o FAIL e il motivo;
- **ripetibile**: dà lo stesso risultato se non è cambiato niente;
- **confrontabile**: scrive un file con data, da confrontare con quello della settimana prima.

<Scene title="Il primo controllo e la sua struttura">
Una funzione per ogni controllo, con lo stesso formato di uscita:

<Log lines={[
  "#!/usr/bin/env bash",
  "set -u                          # errore se uso una variabile mai definita",
  "",
  "esito() {                        # uso: esito PASS|FAIL \"descrizione\"",
  "  printf '%-5s %s\\n' \"$1\" \"$2\"",
  "}",
  "",
  "# 1. Il file delle password cifrate non deve essere leggibile da «altri»",
  "perm=$(stat -c '%a' /etc/shadow)",
  "if [ \"${perm: -1}\" = \"0\" ]; then",
  "  esito PASS \"/etc/shadow non accessibile agli altri ($perm)\"",
  "else",
  "  esito FAIL \"/etc/shadow ha permessi $perm\"",
  "fi",
]} caption="`stat -c '%a'` stampa i permessi in numero; l'ultima cifra riguarda «altri»." />

Il controllo **legge** soltanto. Non c'è nessun `chmod`, nessuna correzione.

<Callout kind="trucco">
`set -u` è una prudenza economica: se sbagli il nome di una variabile, lo script si ferma invece di andare avanti con un valore vuoto e un controllo falso.
</Callout>

<Say who="sensei">Una sola funzione per stampare l'esito. Così le righe sono tutte uguali e si possono confrontare con un diff.</Say>
</Scene>

<Scene title="Altri controlli utili">
Altri esempi, tutti di lettura:

<Log lines={[
  "# 2. Solo root deve avere UID 0",
  "n=$(awk -F: '$3 == 0 {print $1}' /etc/passwd | grep -vc '^root$')",
  "[ \"$n\" -eq 0 ] && esito PASS \"nessun altro account con UID 0\" || esito FAIL \"altri account con UID 0: $n\"",
  "",
  "# 3. Accesso root via SSH (configurazione effettiva, richiede root)",
  "r=$(sshd -T 2>/dev/null | awk '$1 == \"permitrootlogin\" {print $2}')",
  "[ \"$r\" = \"no\" ] && esito PASS \"SSH: root non può entrare\" || esito FAIL \"SSH: permitrootlogin = ${r:-sconosciuto}\"",
  "",
  "# 4. Elenco dei programmi setuid da confrontare con quello precedente",
  "find /usr -xdev -perm -4000 -type f 2>/dev/null | sort > \"setuid-$(date +%F).txt\"",
]} caption="Tre controlli: UID 0, SSH, setuid." />

Alcune osservazioni:

- `sshd -T` stampa la configurazione **effettiva**, non solo quella scritta nel file;
- `grep -vc` conta le righe che **non** corrispondono: qui, gli account diversi da root;
- l'elenco setuid, salvato con la data, si confronta con quello della settimana scorsa: `diff setuid-2026-10-17.txt setuid-2026-10-24.txt`.

<Callout kind="attenzione">
Lo script gira solo sul **tuo** server o su quelli per cui hai un incarico. Controllare configurazioni di macchine altrui senza permesso è accesso abusivo a sistema informatico (art. 615-ter del codice penale), anche se «si legge soltanto».
</Callout>

<Say who="assistente">Il confronto con la settimana precedente è la parte più preziosa: ciò che cambia è quasi sempre ciò che interessa.</Say>
</Scene>

<Scene title="Provare, pianificare, riferire">
Un controllo non provato non vale niente. Il test giusto: **fallo fallire apposta** in una macchina di prova.

<Guided
  steps={[
    "Su una macchina di prova (una tua macchina virtuale) imposta un valore sbagliato, per esempio `PermitRootLogin yes`.",
    "Esegui lo script: deve stampare FAIL su quella riga. Se stampa PASS, il controllo è sbagliato.",
    "Ripristina il valore corretto: ora deve stampare PASS.",
    "Pianifica lo script con cron (modulo F4): un'esecuzione a settimana, con l'uscita salvata in un file con la data.",
    "Alla fine del mese guarda cosa è cambiato tra un file e l'altro: ogni differenza spiegata è una conferma, ogni differenza inspiegata è un'indagine.",
  ]}

<Scene title="Rapporto finale">
<Recap xp={30}>
- Uno script di controllo è di sola lettura, stampa PASS o FAIL con il motivo ed è ripetibile.
- Controlli tipici: permessi di `/etc/shadow` (`stat -c '%a'`), account con UID 0, `sshd -T`, programmi setuid con `find -perm -4000`.
- Si prova facendolo fallire, si pianifica con cron e si confrontano i risultati nel tempo; la correzione la fa una persona, con un cambio annotato.
</Recap>
