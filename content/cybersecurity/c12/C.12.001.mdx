<Scene title="Una cartella, tre esigenze">
Alla «Bianchi Logistica» il server dei file ha la cartella `/srv/progetti`. Appartiene al gruppo `sviluppo`: chi è nel gruppo legge e scrive, gli altri non entrano.

Marta, della contabilità, deve **solo leggere** i file di un progetto per fare le fatture. Il capo sistemista, stanco, propone: «Facciamo `chmod o+r` e finiamo».

<Log lines={[
  "$ ls -ld /srv/progetti",
  "drwxrwx--- 2 root sviluppo 4096 ott 21 09:10 /srv/progetti",
]} caption="Proprietario e gruppo hanno tutto, gli altri niente." />

La domanda del caso: **come dare a Marta il permesso di lettura senza darlo a tutta l'azienda?**

<Scene title="Le ACL: permessi con il nome">
Le **ACL** (Access Control List, «elenco di controllo degli accessi») aggiungono al modello classico delle **voci con nome**: «l'utente marta può leggere», «il gruppo audit può leggere».

Si usano due comandi:

- `setfacl` per impostare;
- `getfacl` per leggere.

<Log lines={[
  "$ sudo setfacl -m u:marta:r-x /srv/progetti",
  "$ getfacl /srv/progetti",
  "# file: srv/progetti",
  "# owner: root",
  "# group: sviluppo",
  "user::rwx",
  "user:marta:r-x",
  "group::rwx",
  "mask::rwx",
  "other::---",
]} caption="`-m` significa «modifica»; `u:marta:r-x` = utente marta, lettura ed esecuzione." />

Sulle cartelle la `x` serve per **entrarci**: senza `x` Marta non potrebbe aprire i file dentro.

<Compare
  caption="Due modi di dare la lettura a Marta."
  left={{ title: "chmod o+r", points: ["Apre la cartella a tutti, non solo a Marta", "Chi non deve vedere i progetti li può leggere"] }}
  right={{ title: "ACL per marta", points: ["Solo l'utente marta può leggere", "Gli altri dipendenti non vedono nulla", "Si toglie con un comando: setfacl -x"] }}
/>

<Callout kind="trucco">
Se `ls -l` mostra un **+** dopo i permessi (per esempio `drwxrwx---+`), quel file ha una ACL. Fai subito `getfacl`: i permessi che vedi con `ls` non sono più tutta la verità.
</Callout>

<Say who="assistente">Il permesso è andato solo a Marta. Gli altri dipendenti continuano a non vedere nulla.</Say>
</Scene>

<Scene title="La mask: il tetto massimo">
Nell'elenco c'è una riga strana: `mask::rwx`. La **mask** è un **tetto**: i permessi delle voci con nome e del gruppo non possono superarla.

Esempio svolto. Il sistemista, per un'altra ragione, fa `chmod g-w` sulla cartella. Con le ACL attive, `chmod g` cambia proprio la **mask**:

<Log lines={[
  "user:marta:rwx          #effective:r-x",
  "group::rwx              #effective:r-x",
  "mask::r-x",
]} caption="Marta ha scritto «rwx», ma il tetto è «r-x»: in pratica può solo leggere." />

<Flow
  caption="La mask taglia i permessi: conta quello effettivo."
  steps={[

    { icon: "shield", title: "Mask", text: "Il tetto: r-x" },

/>

<Callout kind="attenzione">
Quando una ACL «sembra» dare un permesso e non funziona, controlla la colonna **#effective** e la mask. È l'errore più comune.
</Callout>

<Scene title="Le ACL predefinite per i file nuovi">
Altro problema: Marta legge i file che esistono oggi. Ma domani gli sviluppatori creeranno file nuovi. Li vedrà?

**No**, se hai impostato la ACL solo sulla cartella. I file nuovi non ereditano da soli. Serve la ACL **predefinita** (default), che si scrive con `d:`.

<Log lines={[
  "$ sudo setfacl -m d:u:marta:r-x /srv/progetti",
  "$ sudo setfacl -R -m u:marta:r-x /srv/progetti",
]} caption="La prima vale per i file futuri, la seconda per quelli già presenti (`-R` = ricorsivo)." />

Per togliere un permesso:

- `setfacl -x u:marta /srv/progetti` toglie la voce di Marta;
- `setfacl -b /srv/progetti` toglie **tutte** le ACL.

<Callout kind="regola">
Principio del **minimo privilegio**: a ciascuno solo ciò che serve, per il tempo che serve. Le ACL permettono di rispettarlo dove tre caselle non bastano. Ogni ACL che non serve più va tolta.
</Callout>

<Say who="assistente">Due comandi: uno per ciò che c'è, uno per ciò che verrà. Tutti dimenticano il secondo.</Say>
</Scene>

<Scene title="Setuid, setgid e sticky bit">
Esistono tre **permessi speciali**, che compaiono al posto della `x`:

- **setuid** (`s` nella casella del proprietario): chi esegue il programma lo esegue **con i diritti del proprietario**. `passwd` lo usa per poter modificare il file delle password anche se lo lancia un utente normale.
- **setgid** (`s` nella casella del gruppo): su una **cartella** fa sì che i file nuovi prendano il gruppo della cartella. Utile per le cartelle condivise.
- **sticky bit** (`t` in fondo): in una cartella condivisa, ognuno può cancellare **solo i propri file**. È il caso di `/tmp`.

<Log lines={[
  "$ ls -l /usr/bin/passwd",
  "-rwsr-xr-x 1 root root 59976 ... /usr/bin/passwd",
  "$ ls -ld /tmp",
  "drwxrwxrwt 15 root root 4096 ... /tmp",
]} caption="La `s` di passwd è il setuid; la `t` di /tmp è lo sticky bit." />

<Callout kind="attenzione">
Un programma setuid root difettoso o inatteso è una scorciatoia verso i poteri di amministratore. Per questo i difensori li **elencano e li confrontano nel tempo**: un programma nuovo in elenco è un campanello.
</Callout>

Un controllo di lettura, che non modifica niente:

<Log lines={[
  "$ find /usr -perm -4000 -type f 2>/dev/null",
  "/usr/bin/passwd",
  "/usr/bin/sudo",
  "/usr/bin/su",
]} caption="`-perm -4000` cerca i file con il bit setuid." />

<Say who="sensei">Salva l'elenco di oggi. Tra un mese lo confronti con quello nuovo. Quello che compare e nessuno ha installato, lo indaghi.</Say>
</Scene>

<Recap xp={25}>
- Le ACL aggiungono permessi con nome (`setfacl -m u:marta:r-x`) e si leggono con `getfacl`; il segno + in `ls -l` le segnala.
- La mask è il tetto dei permessi: conta la colonna «effective». Per i file futuri serve la ACL predefinita `d:`.
- Setuid, setgid e sticky bit sono permessi speciali: i file setuid vanno elencati e confrontati nel tempo.
</Recap>
