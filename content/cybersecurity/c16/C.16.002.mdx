<Scene title="Tre parti, un sigillo">
Un **JWT** (JSON Web Token, si dice «giot») è una stringa fatta di **tre parti** separate da punti:

- **Header**: dice che tipo di token è e con quale algoritmo è firmato.
- **Payload**: i dati, chiamati **claim**: chi è l'utente, il ruolo, la scadenza.
- **Firma**: un sigillo calcolato su header e payload con una chiave segreta (o con una coppia di chiavi).

Header e payload sono solo **codificati** (in base64url, una scrittura che si legge con qualunque strumento): non sono cifrati. La **firma** non nasconde nulla: serve a **scoprire se qualcuno ha cambiato qualcosa**. Se Elena cambiasse «studente» in «amministratore», la firma non tornerebbe più e il server rifiuterebbe il token.

<Callout kind="regola">
Un JWT è **firmato, non segreto**. Nel payload non si mette nulla che non possa leggere chi ha il token: niente password, niente dati sanitari, niente numeri di telefono.
</Callout>

<Scene title="Che cosa controlla il server">
Quando arriva un token, il server non si limita a «c'è una firma». Controlla, in ordine:

<Guided
  steps={[
    "Firma: è valida con la chiave che il server ha scelto? Se no, scarta.",
    "Algoritmo: è uno di quelli che il server permette? (La scelta la fa il server, non l'header del token.)",
    "Emittente (iss): l'ha emesso il nostro servizio di login?",
    "Destinatario (aud): è stato fatto per questa API e non per un'altra?",
    "Scadenza (exp) e inizio validità: è ancora valido adesso?",
    "Autorizzazione: il ruolo o gli scope dentro il token bastano per **questa** azione?",
  ]}
/>

Un token con firma valida ma scaduto, o emesso per un altro servizio, va comunque rifiutato.

<Say who="sensei">Sei controlli, sempre tutti. Il token buono non chiede di essere creduto sulla parola.</Say>
</Scene>

<Scene title="Gli errori tipici">
Questi errori si trovano davvero nelle revisioni di codice. Li spieghiamo solo per **difendersi**.

- **Segreto debole**: se la chiave di firma è una parola semplice, chi ha un token può provare a indovinarla offline e poi firmare token falsi. La chiave deve essere lunga, casuale e custodita come una password di sistema.
- **Algoritmo non vincolato**: se il server si fida dell'header per scegliere come verificare, un token può chiedere una verifica più debole o nessuna (esiste perfino un valore «none»). Il server deve avere una lista fissa di algoritmi ammessi. Esiste anche la confusione tra chiave segreta e chiave pubblica: si evita con lo stesso principio.
- **Nessuna scadenza, o scadenza di mesi**: un token rubato vale per sempre.
- **Dati sensibili nel payload**: lo vede chiunque abbia il token, compreso chi legge i log.
- **Token conservato dove lo legge uno script**: se la pagina ha un difetto XSS (lo ricordi da C.05), lo script dell'estraneo può portarsi via il token.
- **Nessun modo di revocare**: un JWT valido resta valido finché non scade, anche se l'utente è stato disattivato. Si mitiga con scadenze brevi, controlli aggiuntivi e liste di revoca.

Falsificare token o indovinare chiavi di un sistema che non è tuo è accesso abusivo a sistema informatico (art. 615-ter del codice penale). Si prova solo ciò che è tuo o per cui hai un permesso scritto.
</Callout>

<Scene title="Rapporto finale">
<Recap xp={20}>
- Un JWT ha header, payload e firma: il contenuto si legge, la firma scopre le modifiche.
- Il server controlla firma, algoritmo (deciso da lui), iss, aud, scadenza e permessi per l'azione.
- Errori tipici: segreto debole, algoritmo scelto dal token, scadenze lunghe, dati sensibili nel payload, nessuna revoca.
</Recap>
