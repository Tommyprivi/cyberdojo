<Scene title="Perché le API hanno una lista tutta loro">
Un'**API** è la porta di servizio di un'applicazione: le app, i siti e altri programmi parlano con lei. A differenza di una pagina web, l'API espone **direttamente** gli oggetti dei dati (ordini, utenti, fatture) e le azioni sopra di loro.

Per questo **OWASP** (l'organizzazione che pubblica le liste dei rischi, già incontrata nel modulo C5) ha una lista separata: la **API Security Top 10**, edizione **2023**. Non devi impararla a memoria come una poesia: devi capire **i gruppi**.

<Callout kind="regola">
Quasi tutti i rischi API sono domande che il server dimentica di fare: «chi sei?», «questo è tuo?», «puoi fare questa azione?», «quanto stai chiedendo?».
</Callout>

<Say who="assistente">Una API ben fatta ripete le stesse domande a ogni richiesta, senza fidarsi di quanto detto prima.</Say>
</Scene>

{/* screen */}

<Scene title="I rischi sull'accesso">
Il primo gruppo riguarda chi può vedere o fare che cosa:

- **API1 – Broken Object Level Authorization (BOLA)**: l'API non controlla che l'oggetto richiesto appartenga all'utente. È il caso dell'ordine 5522. **Difesa**: a ogni richiesta, verificare lato server che l'utente abbia diritto a **quell'oggetto**; identificativi non indovinabili aiutano, ma non sostituiscono il controllo.
- **API2 – Broken Authentication**: login, token e recupero password fatti male (nessun limite ai tentativi, token deboli, scadenze assenti). Si lega alle lezioni 1-3.
- **API3 – Broken Object Property Level Authorization**: l'utente può vedere o cambiare **campi** che non dovrebbe, per esempio il campo `ruolo` o `sconto` dentro il suo profilo. **Difesa**: elenco esplicito dei campi leggibili e modificabili, mai «restituisci tutto l'oggetto».
- **API5 – Broken Function Level Authorization**: un utente comune può chiamare una funzione da amministratore (per esempio `DELETE /utenti/12`). **Difesa**: permessi controllati per ogni funzione, con rifiuto di default.

<Scene title="I rischi su risorse, flussi e configurazione">
Gli altri rischi della lista del 2023:

- **API4 – Unrestricted Resource Consumption**: nessun limite a richieste, dimensioni, pagine o costi. Si risolve con limiti e quote (lezione 6).
- **API6 – Unrestricted Access to Sensitive Business Flows**: un flusso utile, come acquistare biglietti o creare account, viene usato in massa da programmi automatici. Difesa: limiti, controlli sui comportamenti anomali, passaggi di verifica.
- **API7 – Server Side Request Forgery (SSRF)**: l'API scarica un indirizzo scelto dall'utente e così può essere spinta a raggiungere servizi interni. Difesa: elenco di destinazioni ammesse e rete interna non raggiungibile.
- **API8 – Security Misconfiguration**: messaggi d'errore troppo dettagliati, CORS aperto, funzioni di debug accese, componenti non aggiornati.
- **API9 – Improper Inventory Management**: nessuno sa quali API esistono. Vecchie versioni (`/v1`) e ambienti di prova restano online, senza controlli.
- **API10 – Unsafe Consumption of APIs**: la tua API si fida troppo dei dati ricevuti da un'altra API (di un fornitore). Difesa: trattare i dati dei partner come input non fidato e convalidarli.

<Callout kind="attenzione">
Provare queste debolezze su servizi che non sono tuoi è accesso abusivo a sistema informatico (art. 615-ter del codice penale). Si prova solo ciò che è tuo o per cui hai un permesso scritto, in un laboratorio isolato.
</Callout>

<Scene title="Rapporto finale">
<Recap xp={20}>
- Il rischio numero uno delle API è l'accesso agli oggetti non propri (BOLA): si controlla il diritto sull'oggetto a ogni richiesta, lato server.
- Oltre all'oggetto si controllano i campi (proprietà) e le funzioni; il filtro non va lasciato all'app.
- Risorse senza limiti, flussi abusati, SSRF, configurazioni errate, inventario confuso e fiducia nei partner chiudono la lista.
</Recap>
